# Joy-Conをスマートフォンにつないで操作する

Joy-Con を **スマートフォンに直接** Bluetoothでつなぎ、
スマートフォンの操作画面（`/controller/`）を Joy-Con で動かせます。

```
[Joy-Con] --Bluetooth--> [スマートフォン]
                          ブラウザ (Gamepad API)
                            ↓ WebSocket
                         trolley_api --> /cmd_vel/phone --> cmd_vel_mux --> trolley_drive
```

画面のタッチスティックはそのまま使えます。Joy-Con は入力源が増えるだけです。

## なぜこの経路にするのか

ロボットPCに Joy-Con を Bluetooth でつなぐ従来の経路
（`joy_node` → `/joy` → `joy_teleop`）では、長時間動かすと
**だんだん遅延が大きくなり、スティックから手を離しても進み続ける**
という症状が出ました。ロボットPCは Wi-Fi で ESP32 へ指令を送りながら
2.4GHz帯で Bluetooth も受けているため、電波の取り合いが起きます。

一方、スマートフォンの操作画面は同じ台車を「びっくりするくらい遅延なく」
動かせていました。そこで **Joy-Con の接続先をスマートフォンへ移す** のが
この機能です。台車側のソフトには手を入れていません。

ブラウザの Gamepad API は、押した瞬間の値を読み出す
**ポーリング方式**（Chromium は 250Hz で読んで共有メモリに置くだけ）で、
溜まっていくキューを持ちません。`/joy` のようにバックログが積もって
遅延が伸びていく構造がそもそも無い、というのがこの経路を選ぶ理由です。

## 準備

### 1. スマートフォンのOSを確認する

| OS | 条件 |
| --- | --- |
| iOS / iPadOS | **16以降**（Joy-ConのOS対応が入ったバージョン） |
| Android | **12以降**。ただし端末による（下記） |

> **Android は端末によってスティックがボタンとして届きます。**
> カーネルの `hid-nintendo` が Joy-Con を掴んだ端末ではアナログの軸で
> 読めますが、掴まない端末では 8方向のハットスイッチ、つまり
> ボタンとして届きます。**どちらでも操作できます**が、
> 後者は「スティック設定」が5歩になります
> （後述の「スティックがボタンとして見えるとき」）。
> アナログで動かしたいなら iOS 16以降の端末が確実です。

ブラウザは **Chrome か Safari** を使ってください。
Firefox は右のJoy-Conのスティックが読めません（後述）。

### 2. Joy-Con をスマートフォンにペアリングする

1. Switch本体から Joy-Con を外し、**本体との接続を切ります**。
   （つながったままだと、スマートフォンから見えません）
2. Joy-Con のレール側、SL と SR の間にある**小さな丸いSYNCボタン**を
   5秒ほど長押しします。ランプが流れるように点滅します。
3. スマートフォンの「設定 → Bluetooth」に `Joy-Con (L)` または
   `Joy-Con (R)` が出るのでタップします。

> **Joy-Con は取り合いになります。**
> スマートフォンにペアリングすると、ロボットPC側・Switch本体側の
> ペアリングは切れます。ロボットPC用とスマートフォン用で
> **別の個体を用意し、テープなどで区別してください。**

### 3. 画面の自動ロックを切る

走行中に画面が消えると停止します（それが安全側の設計です）。
本番前に必ず切ってください。

- iOS: 設定 → 画面表示と明るさ → 自動ロック → **なし**
- Android: 設定 → ディスプレイ → 画面消灯 → 最長

`Screen Wake Lock API` も使っていますが、iOSのホーム画面Webアプリでは
iOS 18.4 より前は効きません。OS側の設定で切るのが確実です。

## 使い方

```
http://<ロボットPCのIP>:8000/controller/
```

1. 上のURLを開きます（従来と同じ画面です）。
2. **画面を1回タップします。**
   iOS ではページをタップしていないとコントローラの入力が届きません。
3. **Joy-Con のボタンをどれか1回押して、離します。**
   ブラウザは「ボタンが押されるまで」コントローラを見せない仕様です
   （指紋採取対策）。画面に出る案内のとおりに操作してください。
4. スティックの下に `Joy-Con: 接続済み` と出たら準備完了です。

### 操作

| 操作 | 動き |
| --- | --- |
| **どれかボタンを押している間**＋スティック | 走行（押している間だけ） |
| ボタンを離す | 即停止 |
| ボタンを1秒押し続ける（操作権が無いとき） | 操作権を要求する |
| 画面のスティックを触る | タッチ操作に切り替わる（Joy-Conより優先） |

- **ボタンはどれでもデッドマンになります。** 端末やJoy-Conの持ち方で
  ボタンの番号が変わるため、「このボタンだけ」と決め打ちにしていません。
  押しやすいボタン（SL / SR / L / ZL など）を握ってください。
- **前後と旋回は排他**です。大きく倒した方の軸だけが使われます
  （タッチ操作・`joy_teleop` と同じ挙動）。
- スティックがボタンとして届く端末では、倒し量が無いぶんを
  **押している時間**で補います（後述の「スティックがボタンとして
  見えるとき」）。
- 走行には操作権が必要です。Switchコントローラが操作権を持っている間は、
  ボタンを1秒押し続けると奪取できます（画面のチップをタップしても同じ）。

### スティックの向きが合わないとき

Joy-Con を横持ちすると、スティックの軸は90度回ります。
左右どちらのJoy-Conかでも変わります（右のJoy-Conは
スティックが `axes[2]/[3]` に出ます）。端末やブラウザによっても違います。

そのため画面から**覚えさせる**ようにしています。30秒で終わります。

1. スティックの下の **「スティック設定」** を押します。
2. 「スティックから手を離してください」→ そのまま待ちます。
3. 「前に進みたい向きへ倒したままにしてください」→ 倒して待ちます。
4. 「右に曲がりたい向きへ倒したままにしてください」→ 倒して待ちます。
5. 「スティックの向きを覚えました」と出れば完了です。
6. **設定が終わったら、ボタンを離して押し直してください。**
   終わった瞬間はスティックが倒れたままなので、そのまま走り出さない
   ようにしてあります。

- **スティックが軸として読めない端末では、手順が5歩に増えます。**
  1回目に倒したときに軸が動かなければ自動で切り替わり、
  前・後・右・左の4方向を覚えます
  （後述の「スティックがボタンとして見えるとき」）。
- 画面を触らずに進みます（倒し続けると次へ進みます）。
- **1歩目は、スティックが中立に戻っていないと進みません。**
  倒したまま中立として覚えてしまうと、前後が反転した設定
  （前に倒すと後退する）が保存されてしまうためです。
  倒れている間は「まだ倒れています」と出ます。
- 覚えた内容は**その端末のブラウザに保存**されるので、次回からは不要です。
  どのコントローラで覚えたかも一緒に保存され、左右のJoy-Conを
  差し替えると自動で捨てます（左右で軸の番号も向きも違うため）。
- 「既定に戻す」で消せます。
- 倒しても動かないとき、画面に
  **「別の軸が動いています。スティック設定をしてください」**
  と出ます。これが出たら設定をやり直してください。

## スティックがボタンとして見えるとき

倒しても走らず、`?debug=1` で見ると
**`axes` がずっと 0 のまま、スティックを倒すと `buttons` に
番号が出る** ことがあります。ボタンには反応するのに
スティックだけが効かない、という形で出ます。

### 原因

**Joy-Con 側の都合です。設定やブラウザの問題ではありません。**

Switch 以外の機器につながれた Joy-Con は「簡易HIDモード」で動き、
スティックを **8方向のハットスイッチ** として報告します。
アナログの値はそもそも送られてきません。
**軸の割り当てをいくら変えても直りません。**

アナログで読むには Joy-Con を「標準フルモード」へ切り替える必要が
あり、それには HID の出力レポートを送れる側
（PCの WebHID、Linux・Android の `hid-nintendo` ドライバ）が要ります。
スマートフォンのブラウザからは送れません。

### どうするか

**ボタンのまま操作できるようにしてあります。**

1. 「スティック設定」を押します。
2. 1回目に倒したときに軸が動かなければ、**自動でボタンの手順に
   切り替わります**（画面に「スティックがボタンとして見えています。
   前後左右を覚えます」と出ます）。
3. 手順は **5歩**になります。中立 → 前 → 後 → 右 → 左。
   軸には符号がありますが、ボタンには無いので4方向とも覚えます。
   （軸で読める端末はこれまでどおり3歩です）
4. 覚えたあとの操作は同じです。ボタンを握りながらスティックを倒します。

覚えた内容は端末に保存されるので、次回からは不要です。

### 押している時間で加速します

倒し量が無いので、押した瞬間から最高速で走ってしまいます。
荷物を載せた台車が飛び出さないよう、**出だしを抑えて**います。

| 押してから | 速さ |
| --- | --- |
| 0秒 | 最高速の 35% |
| 0.8秒 | 最高速 |

- 向きを変えると、出だしの速さからやり直します
  （前進のまま全速で首を振らないため）。
- 一度離すと、次に押したときはまた出だしからです。
- 変えるなら `app.js` の `GAMEPAD_BUTTON_FLOOR`（0.35）と
  `GAMEPAD_BUTTON_RAMP_MS`（800）です。

### 方向のボタンはデッドマンになりません

「どのボタンでもデッドマン」のままだと、
**スティックを倒しただけで走ってしまいます。**
覚えた4方向は自動的にデッドマンから外れるので、走らせるには
**方向とは別のボタン**（SL / SR / L / ZL など）を握ってください。

### 注意

- **斜めは前後と旋回のうち、先に入ったほうを続けます。**
  斜めのあいだ前後と旋回が入れ替わると、台車が首を振るためです。
- 端末によっては斜めが別のボタン番号になり、その間は止まります。
  **まっすぐ倒してください。**
- `timestamp` が値の変化でしか進まない端末では、倒し続けている間
  「入力が固まった」と判定されて8秒で一度止まります（後述の
  「既知の制限」）。いまのところ該当するのは iOS Safari ですが、
  iOS は OS が Joy-Con に対応しているので、この状態にはなりません。

### アナログで動かしたいなら、つなぐ端末を変える

これがいちばん確実です。

- **iOS 16以降の iPhone / iPad**：OS が Joy-Con に対応していて、
  スティックはアナログの軸で出ます。
- **Android で `hid-nintendo` が効いている端末**：同じく軸で出ます。
  効くかどうかは端末のカーネル次第で、Android 12以降でも
  効かない端末があります（今回の症状はこれです）。

## 停止する条件

「押している間だけ走る」ことが、この機能のいちばん大事な性質です。
以下のどれかが起きたら走行指令を送るのをやめます。

| 条件 | 実装 |
| --- | --- |
| ボタンを離した | 毎フレームの判定。即 `{t:'stop'}` |
| コントローラが外れた | `getGamepads()` が null / `connected === false` / 切断イベント |
| 画面が隠れた・別アプリに移った | `visibilitychange` / `blur` / `pagehide` |
| **ブラウザの描画が止まった** | ポーリングが150ms途切れたら送信を止める |
| 入力が変化しない（2秒 or 8秒） | Bluetoothが黙って切れた場合の保険。下記 |
| WebSocketが切れた | `onclose` で停止 |
| 操作権を失った | 状態の更新で停止 |
| **画面のスティックに触った** | Joy-Conより優先。人の側の非常手段 |
| ブラウザが送信をやめた | **サーバ側**が0.3秒でゼロ速度を publish |

**「送信をやめれば0.3秒で止まる」** というのが最後の砦です
（`teleop_ws.py` の `command_timeout`）。
`{t:'stop'}` の送信は「速く止める」ためのもので、
アプリ切替の瞬間などは届かないこともあるため、それには頼っていません。

### 「押し直すまで走らない」

操作者の意思と関係なく止めたとき（フォーカスを失った、画面が隠れた、
反応が無くなった、タッチで割り込まれた）は、**ボタンを一度離して
押し直すまで走行を再開しません。**

止めるだけでは足りないからです。ブラウザはページが隠れている間・
フォーカスを失っている間、ボタンの押下状態を最後の値のまま凍結して
返します。止めた直後の次のフレームで同じ押下を見てしまうので、
すぐに走り出してしまいます。
そのため「そのとき押していたボタン」を一度無視するようにしています。

画面には `ボタンを離してから押し直してください` と出ます。

### 入力が固まったときの判定（2秒 / 8秒）

Bluetoothが黙って切れても、ブラウザは最後の値を返し続けます。
`gamepad.timestamp` の扱いが端末で違うため、判定を2段にしています。

- **値は同じまま `timestamp` だけ進む端末**（Chrome for Android など）
  では、`timestamp` が「受信が続いている」合図になります。
  一度これを観測したら、以後は **2秒** 止まった時点で切ります。
- **`timestamp` が値の変化時しか進まない端末**（iOS Safari）では
  合図として使えないので、軸とボタンが1ビットも変わらない状態が
  **8秒** 続いたら切ります。こちらはまっすぐ全速で走り続けたときに
  誤って発動することがあります（スティックを少し動かせば戻ります）。

どちらも、復帰後はボタンを押し直すまで走りません。

### ポーリングが止まったら送らない、という設計について

ブラウザは画面が消えると `requestAnimationFrame`（描画）を完全に止めますが、
`setInterval`（送信タイマー）は止めずに1秒間隔まで間引いて生かします。

素直に作ると「入力の読み取りだけが凍結し、送信だけが生き残る」ため、
**ボタンを押したままの古い値が1秒おきに送られ続けます。**
サーバ側の0.3秒ウォッチドッグと噛み合うと、
1秒ごとに0.3秒ずつ進むという、止まらない台車になります。

そのため送信側は毎回「最近ポーリングできているか」を確認しています。
画面が消えれば読み取りが止まり、読み取りが止まれば送信も止まります。
`ros2_ws/src/trolley_api/test/test_controller.js` がこの挙動を守っています。

## 現場での確認手順（30秒）

走らせる前に毎回これだけ確認してください。

1. **画面下に `Joy-Con: 接続済み` と出ているか。**
   出ていなければ、画面を1回タップ → ボタンを1回押す。
2. **ボタンを押すと `Joy-Conで走行中` に変わるか**（台車は浮かせておく）。
3. **前に倒すと前に進むか。** 逆なら「スティック設定」をやり直す。
   倒しても何も起きないなら、`?debug=1` で `axes` が動いているかを見る。
4. **ボタンを離すと止まるか。**
5. **画面を切り替えると止まるか**（ホームボタンを押してみる）。

軸の番号やボタンの番号を見たいときは、URLに `?debug=1` を付けて開きます。

```
http://<ロボットPCのIP>:8000/controller/?debug=1
```

画面下にこう出ます。

```
secure=0 pads=1 map=学習(lin:1- ang:0-) axes[0.00, -0.98, 0.00, 0.00] buttons[5] Joy-Con (L) ...
```

スティックがボタンとして届いている端末では、こう出ます。
`axes` が動かず、倒すと `buttons` の番号が変わるのが目印です。

```
secure=0 pads=1 map=学習(btn 前:12 後:13 右:15 左:14) axes[0.00, 0.00, 0.00, 0.00] buttons[5, 12] Joy-Con (L) ...
```

| 項目 | 意味 |
| --- | --- |
| `secure=` | secure context かどうか（Joy-Conの動作には関係ありません） |
| `pads=` | ブラウザから見えているコントローラの台数。`0` ならまだボタンを押していない |
| `map=` | 使っている割り当て。`既定` / `学習(lin:… ang:…)` / `学習(btn 前:… 後:…)` |
| `axes[...]` | 生のスティックの値。前に倒してどれが動くかを見る |
| `buttons[...]` | いま押しているボタンの番号 |

| 症状 | 確認すること |

| `Joy-Con: 画面を1回タップし、ボタンを1回押してください` のまま | 画面を1回タップしてから、Joy-Conのボタンを押す。設定→BluetoothでJoy-Conが「接続済み」か。Joy-ConのLEDが点いているか |
| `ボタンを離してから押し直してください` と出る | そのまま離して押し直す。最初に押されていたボタンは、押しっぱなしのボタンと区別できないので使いません |
| 倒しても動かない。`別の軸が動いています` と出る | 「スティック設定」をやり直す（右のJoy-Conでよく出ます） |
| 倒しても動かない。`スティックがボタンとして見えています` と出る | 「スティック設定」をやり直す。5歩の手順になります（上の「スティックがボタンとして見えるとき」） |

| ボタンで覚えたのに、倒しただけで走る | 方向のボタンはデッドマンから外れているはずです。`?debug=1` で `map=学習(btn …)` になっているか確認してください |
| ボタンで覚えたら遅くなった | 押した瞬間は最高速の35%で、0.8秒かけて最高速になります。仕様です |
| 倒すと逆に動く | 「スティック設定」をやり直す |
| 手を離しても微速で動く | スティックのドリフト。`app.js` の `GAMEPAD_DEADZONE`（既定0.18）を上げる |
| `反応がありません` と出て止まる | Bluetoothを確認。スティックを動かしてボタンを押し直せば復帰します。まっすぐ走り続けた場合にも出ます（下記の制限） |
| `別のコントローラです` と出る | 左右のJoy-Conを差し替えた。覚えた設定は使われないので、スティック設定をやり直す |
| 直したはずの画面が変わらない | ①`colcon build` をやり直す（起動時は `install/` 側の `web/` が使われます）②ブラウザのキャッシュ。`index.html` の `?v=` を上げる。ホーム画面版は作り直す |
| `このブラウザでは使えません` | Chrome か Safari を使う。Firefox Nightly と `privacy.resistFingerprinting` は不可 |
| ボタンを押しても走らない（チップが「Switchで操作中」） | 操作権がない。ボタンを1秒押し続けるか、チップをタップする |
| 走行中に勝手に止まる | 画面の自動ロック。OS側の設定で切る |
| どうしても Joy-Con が見つからない | 下の「見つからないときの逃げ道」を参照 |

## 既知の制限

- **iOSでまっすぐ全速で8秒以上走ると、一度止まることがあります。**
  スティックをいっぱいに倒していると値が1ビットも変化せず、
  「入力が固まった」と判定されるためです（iOSは `timestamp` も
  値が変わるまで更新しません）。**スティックを少し動かして、
  ボタンを押し直せば**復帰します。
  邪魔なら `app.js` の `GAMEPAD_STALE_MS` を大きくしてください。
  ただしこれは「Bluetoothが黙って切れたまま走り続ける時間」でもあります。
  1m/s なら8秒で8m進むので、これ以上長くはしないでください。
- **スティックがボタンとして届く端末では、斜めが効かないことがあります。**
  ハットスイッチの斜めを別のボタン番号として報告する端末では、
  覚えた4方向のどれでもないので止まります。まっすぐ倒してください。
- **ボタンで覚えた場合、微妙な速度調整はできません。**
  倒し量が届かないので、押している時間でしか速さを変えられません。
  細かく寄せたいときは画面のタッチスティックを使ってください。
- **Firefox for Android では右のJoy-Conのスティックが読めません。**
  ブラウザ側が `AXIS_RX/RY` を読まない実装のためです。
  左のJoy-Con か Pro Controller を使うか、Chrome を使ってください。
- **iOSのホーム画面Webアプリ（standalone）** は、iOS 18 より前だと
  Gamepad API が不安定な報告があります。本番前に
  「Safariのタブ」と「ホーム画面版」の両方で確認してください。
- **左のJoy-Conの十字ボタン**は、Androidのキー配置定義に無いため
  ブラウザに出てこない可能性があります。デッドマンには
  SL / SR / L / ZL を使ってください。
- Joy-Con を2本つないでも、1つのコントローラにはなりません
  （PCの joycond のような結合機構がOSにありません）。
  最初に見つかった1台だけを使います。**横持ちの1本**で使ってください。

## 見つからないときの逃げ道

Gamepad API は `http://` のままでも使えます
（Blink・WebKit・Gecko のいずれも secure context を要求していません。
「HTTPS必須」という記事が複数ありますが、実装と一致していません）。
**8000 のURLをそのまま使ってください。**

それでも1台も見つからない場合は、この順で確認します。

1. 画面を1回タップしてから、Joy-Conのボタンを押す（いちばん多い原因）
2. `?debug=1` を付けて開き、`pads=` が 0 のままか確認する
3. ブラウザを変える（Chrome / Safari）
4. OSのBluetooth設定で「接続済み」になっているか確認する

Firefox Nightly と `privacy.resistFingerprinting` を有効にした
Firefox では、非secure contextでコントローラを見せません。
この2つは使わないでください。

## 実装

| ファイル | 役割 |
| --- | --- |
| `ros2_ws/src/trolley_api/web/gamepad.js` | 軸・ボタンの変換だけ。DOMにもWebSocketにも触らない |
| `ros2_ws/src/trolley_api/web/app.js` | ポーリング、入力源の調停、画面、スティック設定 |
| `ros2_ws/src/trolley_api/test/test_gamepad.js` | 変換の単体テスト |
| `ros2_ws/src/trolley_api/test/test_controller.js` | 偽のDOM・Gamepad・WebSocketで `app.js` を動かす結合テスト |

サーバ側（`teleop_ws.py` のプロトコル、`/cmd_vel/phone`、
`cmd_vel_mux` の操作権調停）は変えていません。
ブラウザから送るメッセージも従来と同じ `{t:'cmd', lx, az}` です。

テストは Node.js で動きます（`colcon test` には含まれません）。

```bash
node ros2_ws/src/trolley_api/test/test_gamepad.js
node ros2_ws/src/trolley_api/test/test_controller.js
```

### 入力源の調停

タッチと Joy-Con が同じ値を奪い合わないよう、走行できるのは
どちらか一方だけにしています（`app.js` の `inputSource`）。

- タッチが握っている間は、Joy-Con のポーリングは値を書きません。
- Joy-Con が走行中は、画面のスティックを触っても切り替わりません。
- どちらも、離したときは同じ `stopDriving()` を通ります。
